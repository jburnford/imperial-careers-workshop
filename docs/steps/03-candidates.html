3. Candidate identities

Minutes 20–30. Make the evidence behind a proposed link inspectable.

Records now have local identifiers (henry, agar, illustrated_tree). The next step proposes external identities for the people, so that this small dataset can connect to the Colonial Office List graph and to anything else that uses Wikidata identifiers.

Two sources of candidates:

  • Wikidata, searched with the WikidataMCP vector search and then read statement by statement. The ordinary Wikidata search box matches strings, not meaning, and is not used.
  • The Colonial Office List graph, matched on surname, compatible given names, overlapping career years and a Ceylon posting.

The prompt

Look up candidate identities for these people using the configured Wikidata tools and the supplied Colonial Office List records. Save the retrieved evidence and lookup date. For each candidate, show what supports the match, what conflicts, and what is missing. Leave unresolved cases unresolved. Do not generate QIDs from memory.

Three questions to keep separate

  1. Does the identifier resolve to the retrieved entity? We only show QIDs we fetched. A Q-number supplied from a model’s memory is not a lookup.
  2. Is that entity the one described in this source? Name, type, dates, geography, activity. A real item can still be the wrong person.
  3. What does the connection assert? Linking “Dr. Trimen” in S04 to Q2462643 asserts that this mention refers to that man. It does not assert that every statement on the Wikidata item is true, or that the 1883 “Ceylon” is the modern state.

Keep the evidence for each match. Record unresolved cases as unresolved, with the searches that were run, so that nobody repeats them or mistakes “not found” for “does not exist”.
