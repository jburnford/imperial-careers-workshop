Structure

Minutes 12–22. What is a record here? Python takes the regular entries, a cheap model takes the rest overnight, Python checks the result; you decide what counts as an event.

Terms on this page
  • JSON: a plain-text format for a record: named fields in braces, lists in brackets (see the glossary for Trimen’s).
  • prompt: the written instructions sent to the model with each entry.
  • regex grammar: pattern rules that match text by its shape, written in Python; the deterministic first tier.
  • validator: Python that checks every place and year the model wrote against the source and drops what is not there.
  • post-normaliser: Python that applies the systematic fixes found by the audit, logging each change.
  • vLLM: an open-source server that runs an open model on a GPU and answers like a commercial API.
  • GPU: the graphics card the model runs on; the model has to fit in its memory.
  • token: the unit a model reads and writes in, roughly three-quarters of a word.
  • reasoning mode: a setting where the model writes out its thinking before answering; off here, because it spent the budget and returned nothing.
  • frontier model / open model: a commercial model such as Claude or Gemini, run by its maker; an open model such as Qwen, whose weights you can download and run yourself.
  • deterministic: done by fixed rules, so the same input always gives the same output; no model involved.

All terms: glossary.

The shape of it

Structuring the biographies was never “send them to a model”. It was a hybrid, in three parts, and the same three parts ran twice: once for the Colonial Office List in June 2026, once for the India Office List a week later.

  1. Python first. A regex grammar for the printed entry shape parses what it can. It is all-or-nothing: if any clause containing a year fails to parse cleanly, the whole entry is refused rather than half-parsed. A second Python pass expands the abbreviations it recognises (“Feb.” to “February”, “acctnt.” to “accountant”) and leaves everything else exactly as printed.
  2. A model for what Python cannot do. Binding position to place to time span across run-on, elided, “ditto” and concurrent clauses. One entry in, one JSON object out. For the Colonial Office List the first residue went to a batch API with a cheap commercial model; the bulk of both corpora went to an open model on a university GPU.
  3. Python again. A validator that checks every place and year the model emitted against the source text and drops what it cannot find there. Then a post-normalisation pass that applies the deterministic fixes found by the audit, logging every change.

The schema

One object per entry: surname, given_names, birth_year (only if printed), education, honours with award years, events, and terminal. One event per posting: position and place as printed, year_start, year_end, place_inherited, is_acting, and civil or military. The agent and the historian settled it on a sample before any batch ran.

The prompt, exactly as sent

The system message for every one of the 65,000 entries (file):

You convert ONE printed Colonial Office List biographical entry into a JSON career record. Extract ONLY what is printed; never invent or infer facts.
Rules:
- events: one object per distinct posting. EXPLODE compound/concurrent clauses into separate events (e.g. 'reg.-gen., 1887, and M.L.C., 1889' = two events; 'ag. comsnr., 1915-16; and from 1919' = two events).
- position: as printed (the normalized expansion is fine), e.g. 'assistant colonial secretary'.
- place: the colony, territory, OR locality named in the clause, AS PRINTED (e.g. 'Ceylon', 'Negombo', 'N. Nigeria'). If the clause names no place, carry over the previous clause's place and set place_inherited=true; do NOT guess or upgrade a locality to its parent colony — record exactly what is printed. Inheritance stops when a transfer is stated.
- year_start/year_end: the posting's years; year_end null if a single year.
- is_acting: true when the post is acting ('ag.'/'acting').
- org_type: 'military' for army/navy/regiment/expedition/campaign postings, else 'civil'.
- honours: decorations/orders with their AWARD year if printed in parentheses (e.g. 'C.M.G. (1905)'); these award-years are NOT career events.
- birth_year: only if explicitly printed ('B. 1872'); else null. NEVER infer from the earliest career date.
- education: the 'ed. ...' string as one metadata string; university class honours stay here, NOT as events.
- terminal: {kind: retired|resigned|died|pensioned|other, year} if the entry states the career ended, else null.

Return ONE JSON object with EXACTLY these top-level keys: surname, given_names, birth_year, education, honours, events, terminal. Split the headword into surname + given_names (no 'name'/'person' key). Each honour is {"award": str, "year": int|null} (no 'decoration'/'order' key).

The user message is the entry alone, after the abbreviation pass. Trimen’s 1889 entry goes in like this (file):

TRIMEN, HENRY, M.B. (Lond.), F.R.S., F.L.S. —Formerly lecturer on botany at St. Mary's Hospital, London, 1867 to 1875; was senior assistant to department of botany, British Museum, 1869 to 1879; director Royal Botanical Gardens, Ceylon, February, 1880; author of numerous works and papers on pure and applied botany.

Three things to notice. Every rule in the list exists because an earlier run broke it; the rule about birth years is there because a model had been inferring them from the first appointment. The last paragraph pins the key names, because a bake-off found the model drifting to name and decoration without it. And nothing in the prompt is about the historical question; it is entirely about what the page says and how to hold it.

The overnight run

Colonial Office List India Office List
Model Qwen3.6-35B-A3B, served by vLLM on a university GPU box same
Settings temperature 0, reasoning off, 8 to 16 workers, 4 retries same
Entries 34,743 30,496
Rate once warm about 1 a second 1.03 a second
Elapsed about a day including setup, 19–20 June 8.24 hours, overnight 25–26 June
Failed to return valid JSON 55, under 0.2 per cent

The handoff note records the setting that matters most: reasoning off. With it on, long entries eat the token budget and return no JSON, a 67 per cent failure rate. Thinking off, temperature zero: the same finding every run on this corpus has made.

The India Office List needed one new piece of code, a Python segmenter for its different OCR format, written that morning. The prompt, the model, the validator and the post-normaliser were reused unchanged through one environment variable. The graph was published that afternoon.

Two kinds of model

A frontier model, in session as the coding agent, structured about 200 entries by hand as the reference set and wrote everything in the list above. The open model inside the script read the corpus. Every record says which path produced it. The runbook for the in-session loop is saved.

What came back

Trimen’s entry, structured (saved):

position place years
lecturer on botany London 1867–1875
senior assistant to department of botany British Museum 1869–1879 overlaps the first: two concurrent posts, two events
director Royal Botanical Gardens Ceylon 1880–

Plus education: "M.B. (Lond.)", two honours without years, no birth year, no terminal event. In the published graph the first and third events are placed; “British Museum” is an institution, not a place, and stays unplaced.

The audit

Structured records were read against their source by a reviewer model, in three rounds, and the findings categorised (catalogue, round 1 pairs). The figures are before the post-normaliser described below:

Round Sample Fully clean Major error
1 every tenth of the first 1,859 records: 186 129 (69%) 8 (about 3%)
2 100 spread across the corpus 51 (51%) 9 (about 9%)
3 300 spread across the corpus about 149 (50%) not tallied

Round 1 was front-loaded on early, simple entries; the later rounds reach the dense twentieth-century careers and the peerage entries, and are the better estimate. A model did the reading in all three; the examples below were checked by hand.

Three of the findings, source beside record (saved):

The ditto that was not resolved. Balmer’s last clause, “senr. dep. P.M.G., do., 1935”, came back with place: "do.". The rule says inherit; the model copied the abbreviation.

The appointment date that became a birth year. “BLAKELY, DONALD QUENTIN.—Clk., atty.-gen.’s off., B. Honduras, Apl., 1898.” came back with birth_year: 1898 and an event with no year. The prompt forbids exactly this. The same record expanded “off.” to “officer” instead of “office”.

The knighthood split in two. “KT. BACH. (1920)” came back as two honours, KT and BACH (1920). Three records in the sample did the same.

Why the fix was not a bigger model

The errors are not random. They are a handful of systematic patterns: a short list of abbreviations mis-expanded the same way every time, ditto marks left literal, one compound honour split, “mentioned in despatches” dropped. Each has a deterministic fix, and those fixes are the post-normalisation pass: merge KT + BACH into Knight Bachelor; forward-fill a “do.” place from the previous event and set the flag; strip honorifics folded into given names; “officer in chief” back to “officer in charge”; drop a military tag with no military signal in the position. Every change is appended to a list on the record, so nothing is silent. The “off.” expansion is fixed one step earlier, by not pre-expanding ambiguous abbreviations at all.

A frontier model on every entry would have cost more, taken longer, and still needed the audit.

You decide: what is an event. Whether an acting appointment is a posting. Whether “called to the bar, 1879” belongs in the career. Whether “leader of leg. coun. from 1906 to 1911” is a position or a description. The prompt records those decisions; the audit checks whether the model kept them; the post-normaliser enforces the ones that can be enforced.
