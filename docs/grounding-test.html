Side experiment: twenty entries, three workflows

Not part of the hour. Can a chatbot supply Wikidata identifiers from memory, and what does retrieval cost in time? A saved test from 7 October 2026.

Terms on this page
  • QID: a Wikidata identifier: Q plus a number.
  • retrieval: the model searches the web or a database and reads what it finds, instead of answering from memory.
  • frontier model: the most capable models, from Anthropic, OpenAI and Google, reached only through their services.
  • open-weight model: a model whose trained weights can be downloaded and run anywhere. Frontier and open-weight are different properties, not opposites.

All terms: glossary.

In short: a chatbot without tools supplied sixteen person identifiers for twenty printed entries, and none was right. Two models with web retrieval supplied sixteen each, all right, but took twenty to twenty-seven minutes. A name understood is not an identifier verified, and verification takes time.

The runs

Twenty long entries were chosen on 7 October 2026: twelve for people the pipeline grounded, eight it did not. For an optional follow-up, paste one into a chatbot with no tools: “Who is this? Give the Wikidata QID.” Then look the answer up. Score it: right, wrong item, invented identifier, or declined. The answer key has the pipeline’s QID and the MCP lookups.

What the lookups already show: of the eight the pipeline left ungrounded, three have a plausible item the vector search finds at once (Price, Henry Francis Wilson, T. J. Alldridge) and five have nothing in the top fifty. “Not grounded” means the gate did not accept; it never means “no such item”.

And the control. On 7 October Jim pasted the twenty entries into Gemini 3.8 Flash with no tools: “Parse these bios and ground the places, schools and people to Wikidata ids where possible.” The response is fluent and well organised, supplies plausible names and many identifiers. Scored against Wikidata:

Correct 0
Resolve to something that is not a person (a plant, a patent, Thoth, an Iranian village, an archive series, a reptile) 6
Within a few thousand of the right number 7
Place, school and other-person identifiers given 142
Whose Wikidata label matches the name 43

The matches are the famous, low-numbered items: Paris, Canada, Singapore, Churchill. Nyasaland resolved to a disambiguation page, the Straits Settlements to a Danish triathlete, the Cape Colony to an Austrian goalkeeper, Joseph Chamberlain to a Swiss footballer. The model knew who; it did not know the number. A Q-number from memory is a string the model has seen near a name, and nothing in the response tells you which ones resolve.

The same day, the same twenty entries went to Claude Opus 5.5 in a chat with web search, with the same prompt; it reported only identifiers it had seen on a page (response, scoring). Sixteen identifiers given, sixteen right, the same four declined. It found Prince, whom the vector search had missed, and it found that Gorges has two Wikidata items for one man. It also stopped at its tool limit before reaching a single place name; a second pass finished the schools and the other people and reached 17 of 138 places (CSV, 75 identifiers, all verified). Its first memory guess for George V was Q269, which is Tashkent; it caught that itself by reading the page.

A third run, GPT Astra 6 at the medium setting with web retrieval, took 27 minutes and produced a structured file of 180 entities with offsets, confidence, a relation type, rejected candidates with reasons and dated evidence (scoring). All 155 identifiers passed the saved label/alias check; that check does not establish that every match fits its historical context. It grounded Ceylon, the Straits Settlements, the Union of South Africa and the rest to the period polities, and it recorded Penang Q188096, the item the pipeline had wrongly matched, as a modern proxy only. The file still maps one colonial Victoria to the modern state, and its “Malay States” match needs review. At about 80 seconds an entry, a serial extrapolation over 27,526 people is about 25 days. That is an illustration of throughput at the observed rate, not a forecast: parallel requests, caching, shorter entries and different tools would change it.

These runs show why an identifier must be retrieved and checked. They do not rank models or isolate the effect of retrieval: model, tools and output coverage all differ. The place counts use different units and are not comparable accuracy scores. Even a retrieved, correctly labelled item can be the wrong historical match.

Use retrieval on hard cases and a reference sample, then have a historian review the decisions before treating them as a standard. Record wall-clock time, model charges and human review time separately. A slow demonstration is evidence about this run, not a general price comparison.

Two jobs; measure their costs

Two different jobs need different kinds of model, and each has its own costs to measure.

Job What the project used What to measure
Write and repair the pipeline Frontier coding agent (Claude Code) Session cost and historian time
Read the collection Open model (Qwen) on a desktop GPU or cluster Throughput, GPU time, failures and audit time
Review hard cases Retrieval with a capable model Lookup cost and time per case

The slowest retrieval run took 27 minutes for 20 entries, about 80 seconds each. Run one after another for the 27,526 Colonial Office person records, that rate would take about 25 days. That is a serial extrapolation at the observed rate, not a forecast or an invoice: caching and parallel requests change throughput, and campus computing is not free even without a per-request bill. Retrieval suits the review queue, not the whole corpus.

Start with twenty records. No cluster is needed for a first trial; a hosted model is enough. The worked cost estimate shows how to price reading a whole collection from measured tokens.
